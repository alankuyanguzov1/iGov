# Архитектурные решения (ADR)

## ADR-01: Единое Next.js приложение вместо трех отдельных проектов

Дата: 17.07.2026. Статус: принято.

Требование логического разделения landing / frontend / backend реализовано внутри монорепозитория: лендинг изолирован как route group `(landing)` со своей папкой компонентов, основное приложение живет в route group `(app)`, серверная логика (миграции Supabase, движок правил, контент льгот) вынесена в `/backend`. Физически деплоится одно Next.js приложение на Vercel.

Причины: один деплой вместо трех, мгновенный роутинг между лендингом и приложением, один набор дизайн-токенов, меньше конфигурации для команды из двух человек. Если лендинг понадобится выделить физически, route group выносится в отдельный проект без переписывания компонентов.

## ADR-02: Eligibility считает детерминированный rules engine, не ML

Дата: 17.07.2026. Статус: принято.

Право на льготу определяется законом детерминированно, поэтому мэтчинг реализуется как движок правил (чистые функции TypeScript + параметры из БД, unit-тесты, ссылка на статью НПА у каждого правила) по образцу OpenFisca. LLM используется только для офлайн-генерации черновиков карточек «Понятный закон» с обязательной ручной верификацией перед публикацией. Модель никогда не решает, положена ли льгота.
